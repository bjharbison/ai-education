Lab 01
Run an LLM Locally with Ollama + Open WebUI
⏱ ~45 min Beginner 💰 Free 🖥️ macOS · Windows · Linux

What You'll Build

A fully self-hosted LLM accessible via a ChatGPT-like web UI on your local network, plus an OpenAI-compatible REST API you can call from any application.

Prerequisites

  • 8+ GB RAM (16 GB recommended for 7B models)
  • ~10 GB free disk space
  • Internet connection for initial model download
  • No GPU required (CPU inference works, just slower)

Step-by-Step Instructions

  1. Install Ollama

    macOS / Linux: Run curl -fsSL https://ollama.com/install.sh | sh in your terminal. Ollama will install as a background service that auto-starts on login.

    Windows: Download the installer from ollama.com and run it. Ollama runs as a system tray app.

    Verify: ollama --version should print something like ollama version 0.5.x

  2. Pull your first model

    Run: ollama pull llama3.2:3b-instruct-q4_K_M

    Ollama downloads the quantized model weights (~2 GB). Progress is shown in the terminal. Ollama stores models in ~/.ollama/models (Linux/Mac) or %USERPROFILE%\.ollama (Windows).

  3. Run a quick chat test in the terminal

    ollama run llama3.2:3b-instruct-q4_K_M

    This opens an interactive chat session. Try a few prompts. Type /bye to exit. Note the tokens/second rate printed at the end of each response.

  4. Deploy Open WebUI with Docker

    Make sure Docker Desktop is installed, then run:

    bash
    docker run -d \
  --name open-webui \
  --network=host \
  -v open-webui:/app/backend/data \
  -e OLLAMA_BASE_URL=http://127.0.0.1:11434 \
  --restart always \
  ghcr.io/open-webui/open-webui:main

    On Windows/macOS (Docker Desktop without host networking): use http://host.docker.internal:11434 for the URL and add -p 3000:8080 instead of --network=host.

  5. Open the web interface

    Navigate to http://localhost:3000 (or http://localhost:8080 if you changed the port). Create an admin account on first launch. You should see a ChatGPT-style interface with your Llama model available in the model dropdown.

  6. Test the OpenAI-compatible REST API

    Ollama exposes an OpenAI-compatible API on port 11434. Test it with curl:

    bash
    curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llama3.2:3b-instruct-q4_K_M",
    "messages": [
      {"role": "user", "content": "Explain transformers in 2 sentences."}
    ],
    "stream": false
  }'

    Or use it from Python with the OpenAI SDK: pip install openai, then set base_url="http://localhost:11434/v1" and api_key="ollama".

  7. Pull additional models and compare

    Pull 2–3 different models: ollama pull mistral:7b-instruct-q4_K_M, ollama pull gemma2:2b, ollama pull phi3:mini. In Open WebUI, start a conversation and switch models mid-thread to compare response quality and speed. Note the tokens/sec difference between model sizes.

  8. Measure and record baseline performance

    For each model you've pulled, run this Python script to measure tokens/second and note the results — you'll use these numbers in Lab 08 (Benchmarking).

    Pythonbenchmark_ollama.py
    import time, requests, json

MODEL   = "llama3.2:3b-instruct-q4_K_M"
PROMPT  = "Explain the transformer architecture in detail."

start = time.time()
resp = requests.post(
    "http://localhost:11434/api/generate",
    json={"model": MODEL, "prompt": PROMPT, "stream": False}
)
elapsed = time.time() - start

data = resp.json()
tokens = data.get("eval_count", 0)
tps    = tokens / elapsed

print(f"Model:      {MODEL}")
print(f"Tokens:     {tokens}")
print(f"Time:       {elapsed:.1f}s")
print(f"Throughput: {tps:.1f} tok/s")

What You've Accomplished

  • A running local LLM with no API costs or privacy concerns
  • A web-based chat UI accessible from any device on your LAN
  • An OpenAI-compatible API endpoint for application development
  • Baseline performance numbers for Lab 08 benchmarking

Run an LLM Inside a Virtual Machine
⏱ ~1.5 hrs Beginner 💰 Free 🖥️ VirtualBox · VMware · Ubuntu
Covers: M6 · Model ServingM6 · MLOps

GPU Passthrough Note

VirtualBox does not support GPU passthrough for CUDA. For GPU-accelerated inference inside a VM, use VMware Workstation Pro (Windows/Linux) or configure KVM with VFIO on Linux. This lab runs CPU-only Ollama inside the VM, which works fine for learning.

VM Setup

  1. Download VirtualBox and Ubuntu Server

    Download VirtualBox from virtualbox.org. Download Ubuntu Server 24.04 LTS ISO from ubuntu.com/download/server. Ubuntu Server is preferred over Desktop for this lab — it's lighter and mirrors real cloud servers.

  2. Create the VM

    In VirtualBox Manager, click New. Settings: Name = ai-lab, Type = Linux, Version = Ubuntu 24.04 LTS (64-bit). RAM: allocate at least 8 GB (12–16 GB if you have it). CPUs: at least 4. Disk: 50 GB dynamically allocated VDI.

    In Settings → Network: set Adapter 1 to Bridged Adapter (not NAT). This gives the VM its own IP on your LAN, making it accessible from other devices.

  3. Install Ubuntu Server

    Boot from the ISO, follow the installer. Choose "Ubuntu Server (minimized)" profile. Set a memorable username/password. Enable OpenSSH Server when prompted — this lets you SSH in from your host instead of using the VirtualBox console.

  4. SSH into the VM from your host

    After the VM boots, find its IP: ip a | grep inet inside the VM. Then from your host terminal: ssh youruser@VM_IP_ADDRESS. From here, all remaining commands run in this SSH session.

  5. Update the system and install Ollama

    bashinside the VM
    sudo apt update && sudo apt upgrade -y
curl -fsSL https://ollama.com/install.sh | sh
sudo systemctl enable --now ollama
ollama pull llama3.2:3b-instruct-q4_K_M

  6. Expose Ollama on the network interface

    By default, Ollama only listens on 127.0.0.1. To accept connections from your host machine, edit the systemd service:

    bash
    sudo systemctl edit ollama

# Add these lines in the editor that opens:
[Service]
Environment="OLLAMA_HOST=0.0.0.0"

sudo systemctl daemon-reload
sudo systemctl restart ollama

  7. Install Docker and Open WebUI in the VM

    bash
    # Install Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker

# Run Open WebUI
docker run -d \
  --name open-webui \
  -p 3000:8080 \
  -e OLLAMA_BASE_URL=http://172.17.0.1:11434 \
  -v open-webui:/app/backend/data \
  --restart always \
  ghcr.io/open-webui/open-webui:main

    Open http://VM_IP:3000 in your browser on the host machine.

  8. Create a VM snapshot

    In VirtualBox, with the VM running, go to Machine → Take Snapshot. Name it "Clean Ollama Install". This is your restore point — if you break something during later experiments, you can revert here instantly. This is your first taste of immutable infrastructure.

Headless VM Management

You can start/stop the VM without a GUI: VBoxManage startvm ai-lab --type headless and VBoxManage controlvm ai-lab poweroff. Add these as shell aliases for convenience.

Deploy on AWS Free Tier (EC2)
⏱ ~2 hrs Intermediate 💰 ~$0 free tier 🖥️ AWS EC2
Covers: M6 · ServingM6 · MLOpsM6 · Monitoring
Covers: M6 · Serving M6 · MLOps M6 · Monitoring
Cost Warning
Cost Warning: AWS Free Tier gives 750 hours/month of t2.micro (1 vCPU, 1 GB RAM) or t3.micro for the first 12 months. A t2.micro is too small for most LLMs — use it for the API/proxy layer only, or upgrade to t3.medium (~$0.04/hr) and terminate when done. Always set a billing alert before proceeding.

Recommended Instance Sizes

🆓
t2.micro

1 vCPU, 1 GB RAM. Free 12 months. API proxy only — too small for Ollama.

🧮
t3.medium

2 vCPU, 4 GB RAM. ~$0.04/hr. Handles 1B models only.

🚀
t3.xlarge

4 vCPU, 16 GB RAM. ~$0.17/hr. Runs 3B–7B INT4 models.

⚡
g4dn.xlarge

4 vCPU, 16 GB RAM, T4 GPU (16 GB VRAM). ~$0.53/hr. Fast 7B inference.

  1. Create an AWS account and set billing alerts

    Sign up at aws.amazon.com. Immediately go to Billing → Budgets → Create Budget. Set a Zero Spend Budget — AWS will email you the moment any charge occurs. This is non-optional.

  2. Launch an EC2 instance

    Go to EC2 → Launch Instance. Choose Ubuntu Server 24.04 LTS. Select your instance type (t3.xlarge recommended for actual LLM inference). Create a new key pair (RSA, .pem format) and download it — you can't recover this later.

    In the network settings, allow: SSH (port 22, your IP only), HTTP (port 80, anywhere), HTTPS (port 443, anywhere), and custom TCP 11434 from your IP only (for direct Ollama access during testing).

  3. Connect via SSH

    bash
    chmod 400 ~/Downloads/your-key.pem
ssh -i ~/Downloads/your-key.pem ubuntu@YOUR_EC2_PUBLIC_IP

  4. Install Ollama and pull a model

    bash
    # Update and install Ollama
sudo apt update && sudo apt install -y curl
curl -fsSL https://ollama.com/install.sh | sh

# Expose on all interfaces
sudo mkdir -p /etc/systemd/system/ollama.service.d
echo -e "[Service]\nEnvironment=OLLAMA_HOST=127.0.0.1" \
  | sudo tee /etc/systemd/system/ollama.service.d/override.conf
sudo systemctl daemon-reload && sudo systemctl restart ollama

# Pull a model (choose based on your instance RAM)
ollama pull llama3.2:3b-instruct-q4_K_M

  5. Install and configure Nginx as a reverse proxy

    nginx/etc/nginx/sites-available/ollama
    sudo apt install -y nginx apache2-utils

# Generate a password file for basic auth
sudo htpasswd -c /etc/nginx/.htpasswd yourusername

# Create the nginx config
sudo tee /etc/nginx/sites-available/ollama <<'EOF'
server {
    listen 80;
    server_name YOUR_EC2_PUBLIC_IP;

    location / {
        auth_basic "LLM API";
        auth_basic_user_file /etc/nginx/.htpasswd;

        proxy_pass http://127.0.0.1:11434;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        client_max_body_size 10M;
    }
}
EOF

sudo ln -s /etc/nginx/sites-available/ollama /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

  6. Test from your local machine

    bash
    # From your local machine:
curl http://YOUR_EC2_IP/api/generate \
  -u "yourusername:yourpassword" \
  -H "Content-Type: application/json" \
  -d '{"model":"llama3.2:3b-instruct-q4_K_M","prompt":"Hello!","stream":false}'

  7. STOP your instance when done

    In the EC2 console, select your instance → Instance State → Stop (not terminate — stopped instances don't incur compute charges, only minimal EBS storage charges). Set a calendar reminder to terminate it if you won't return within a week.

AWS Free Tier Reality Check

The free tier t2.micro (1 GB RAM) cannot meaningfully run any current LLM — it can host the nginx proxy but not Ollama itself. For actual LLM inference, you need at least a t3.medium (~$0.04/hr). Run it for 4 hours, terminate it, and you've spent $0.16 total. That's an excellent learning-to-cost ratio.

Why Oracle Over AWS for Free Inference

AWS free tier gives you 1 GB RAM for 12 months. Oracle gives you 24 GB RAM forever. For a self-hosted LLM API that doesn't cost anything to run indefinitely, Oracle is the clear winner. The catch: Oracle's A1 ARM machines sometimes have availability issues — if "Out of Capacity" appears, try a different region or try again the next day.

Synology NAS CPUs (Intel Celeron/Atom, AMD Ryzen, or ARM) are not designed for LLM inference. A typical NAS CPU will generate 1–6 tokens/second for a 3B INT4 model. #include <cuda_runtime.h>

#define CHECK(call) { \

    if (err != cudaSuccess) { \
        printf("CUDA error: %s at line %d\n", cudaGetErrorString(err), __LINE__); \
        exit(1); \
    } \
}

// ── YOUR TASK: implement this kernel ─────────────────────────
__global__ void vecAdd(float* A, float* B, float* C, int N) {
    // TODO: compute global thread index
    // TODO: bounds check
    // TODO: C[i] = A[i] + B[i]
}

int main() {
    const int N = 1 << 24;  // 16M elements
    size_t bytes = N * sizeof(float);

    // Host allocation + initialization
    float *h_A = (float*)malloc(bytes);
    float *h_B = (float*)malloc(bytes);
    float *h_C = (float*)malloc(bytes);
    for (int i = 0; i < N; i++) { h_A[i] = 1.0f; h_B[i] = 2.0f; }

    // Device allocation
    float *d_A, *d_B, *d_C;
    CHECK(cudaMalloc(&d_A, bytes));
    CHECK(cudaMalloc(&d_B, bytes));
    CHECK(cudaMalloc(&d_C, bytes));

    // Copy to device
    CHECK(cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice));
    CHECK(cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice));

    // Launch kernel
    int threadsPerBlock = 256;
    int blocksPerGrid = (N + threadsPerBlock - 1) / threadsPerBlock;
    vecAdd<<<blocksPerGrid, threadsPerBlock>>>(d_A, d_B, d_C, N);
    CHECK(cudaGetLastError());
    CHECK(cudaDeviceSynchronize());

    // Copy result back and verify
    CHECK(cudaMemcpy(h_C, d_C, bytes, cudaMemcpyDeviceToHost));
    for (int i = 0; i < N; i++) {
        if (h_C[i] != 3.0f) { printf("FAIL at %d\n", i); return 1; }
    }
    printf("PASS: All elements correct\n");

    cudaFree(d_A); cudaFree(d_B); cudaFree(d_C);
    free(h_A); free(h_B); free(h_C);
    return 0;
}

  3. Exercise 2 — Tiled Matrix Multiplication

    Implement matrix multiplication using shared memory tiling to reduce global memory bandwidth. Compare performance against a naive (no-shared-memory) version. The speedup demonstrates why shared memory is one of the most important CUDA optimization techniques.

Once you've written raw CUDA, try implementing the same kernels in OpenAI Triton (pip install triton). Triton abstracts the threading model but gives you explicit control over memory access patterns. The same softmax you wrote in 100 lines of CUDA can be written in 30 lines of Triton with comparable performance.

  2. Build a performance benchmarking harness

    Pythonbenchmark.py
    import time, statistics, torch, psutil, json
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

def benchmark_model(model_id, quant_config=None, n_runs=20, max_new_tokens=200):
    """Measure TTFT, generation throughput, and peak memory."""
    
    model = AutoModelForCausalLM.from_pretrained(
        model_id,
        quantization_config=quant_config,
        device_map="auto",
        torch_dtype=torch.float16 if quant_config is None else None,
    )
    tokenizer = AutoTokenizer.from_pretrained(model_id)
    
    test_prompt = "Explain the attention mechanism in transformers in detail."
    inputs = tokenizer(test_prompt, return_tensors="pt").to("cuda")
    
    # Warmup
    with torch.no_grad():
        model.generate(**inputs, max_new_tokens=50)
    torch.cuda.synchronize()
    torch.cuda.reset_peak_memory_stats()
    
    ttft_list, tps_list = [], []
    
    for _ in range(n_runs):
        start = time.perf_counter()
        first_token_time = None
        
        with torch.no_grad():
            output = model.generate(
                **inputs,
                max_new_tokens=max_new_tokens,
                do_sample=False,
            )
        torch.cuda.synchronize()
        end = time.perf_counter()
        
        n_tokens = output.shape[-1] - inputs.input_ids.shape[-1]
        total_time = end - start
        
        ttft_list.append(total_time / n_tokens)  # approx TTFT = time/first_token
        tps_list.append(n_tokens / total_time)
    
    peak_mem_gb = torch.cuda.max_memory_allocated() / 1e9
    
    return {
        "model":      model_id,
        "quant":      "fp16" if quant_config is None else "int8/int4",
        "tps_median": round(statistics.median(tps_list), 1),
        "tps_p95":    round(statistics.quantiles(tps_list, n=20)[0], 1),
        "peak_mem_gb":round(peak_mem_gb, 2),
    }

# Run benchmarks across formats:
results = []

# FP16 baseline
results.append(benchmark_model("meta-llama/Llama-3.2-3B-Instruct"))

# INT8
results.append(benchmark_model(
    "meta-llama/Llama-3.2-3B-Instruct",
    BitsAndBytesConfig(load_in_8bit=True)
))

# INT4 (NF4)
results.append(benchmark_model(
    "meta-llama/Llama-3.2-3B-Instruct",
    BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4")
))

# Print results table
print(f"{'Model':<40} {'Quant':<8} {'TPS (p50)':<12} {'TPS (p5)':<12} {'Peak VRAM'}")
print("-" * 85)
for r in results:
    print(f"{r['model']:<40} {r['quant']:<8} {r['tps_median']:<12} {r['tps_p95']:<12} {r['peak_mem_gb']:.2f} GB")

Key Takeaway

After this lab you'll have a concrete, personal dataset of LLM performance numbers on your own hardware — far more useful than reading benchmarks that used different GPUs, different prompts, and different batch sizes. Hardware characteristics, quantization format, and model architecture all interact in ways that only hands-on measurement reveals.
